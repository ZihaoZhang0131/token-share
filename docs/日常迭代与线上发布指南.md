# Token Station 日常迭代与线上发布指南

> 适用项目：`Token Station v1`
> 生产域名：`https://tokenshare.asia`
> 生产目录：`/opt/token-station`
> 服务器：阿里云轻量应用服务器 `47.253.135.70`
> 文档日期：2026-08-18

## 1. 发布原则

每次发布固定按以下顺序执行：

```text
本地开发
  → 本地测试
  → Git 提交并推送 GitHub
  → 备份线上数据库
  → rsync 演练
  → rsync 正式同步
  → Docker Compose 重建
  → 健康检查和业务验收
```

基本规则：

- GitHub `main` 分支是已提交代码的版本记录。
- 服务器的 `.env`、数据库卷、Redis 卷和证书卷不从本地同步。
- 上线前必须备份；正式同步前必须先执行 `rsync -n` 演练。
- 日常更新使用 `docker compose up -d --build`，不再运行首次签发证书用的 `enable-tls.sh`。
- 绝对不执行 `docker compose down -v`。

## 3. 在本地完成开发和检查

进入本地项目：

```bash
cd '/Users/markov/Desktop/token中转站'
```

运行后端测试与静态检查：


检查 Git 变更：


满足以下条件才继续：

- Pytest 全部通过。
- Ruff 没有错误。
- TypeScript 类型检查通过。
- Vite 生产构建成功。
- `git diff --check` 没有输出。

## 4. 提交并推送 GitHub

查看待提交文件：

```bash
git status --short
```

提交并推送：

```bash
git add -A
git commit -m "简短描述本次修改"
git push origin main
```

示例：

```bash
git commit -m "fix nginx tls startup"
git push origin main
```

推送后确认本地与远程一致：

```bash
git status --short --branch
git log -1 --oneline --decorate
```

`git push` 只会更新 GitHub，不会自动更新生产服务器。

## 5. 备份线上数据库

在 Mac 上执行：

```bash
ssh -o IdentitiesOnly=yes \
  -i /Users/markov/Desktop/mac_air.pem \
  root@47.253.135.70 \
  'cd /opt/token-station && ./scripts/backup.sh && docker compose ps'
```

输出应包含：

```text
Backup created: ./backups/token-station-YYYYMMDDTHHMMSSZ.sql.gz
```

记下输出中的实际备份文件名，然后在服务器校验压缩包：

```bash
cd /opt/token-station
ls -lh backups
latest_backup=$(ls -1t backups/token-station-*.sql.gz | head -n 1)
printf 'Checking backup: %s\n' "$latest_backup"
gzip -t "$latest_backup"
```

`gzip -t` 无输出且返回命令行，表示压缩包结构正常。同时检查 `ls -lh` 显示的文件不是异常小的空备份。

大版本、数据库迁移、认证或密钥逻辑修改前，同时在阿里云控制台创建一份系统盘快照。

## 6. 用 rsync 演练本次同步

先在 Mac 上执行演练命令：

```bash
rsync -avzn --delete --itemize-changes \
  --exclude '.git' \
  --exclude '.env' \
  --exclude '.DS_Store' \
  --exclude '.venv' \
  --exclude '.pytest_cache' \
  --exclude '.ruff_cache' \
  --exclude 'frontend/node_modules' \
  --exclude 'frontend/dist' \
  --exclude 'frontend/*.tsbuildinfo' \
  --exclude 'frontend/vite.config.js' \
  --exclude 'frontend/vite.config.d.ts' \
  --exclude '*.db' \
  --exclude 'backups' \
  -e 'ssh -o IdentitiesOnly=yes -i /Users/markov/Desktop/mac_air.pem' \
  '/Users/markov/Desktop/token中转站/' \
  root@47.253.135.70:/opt/token-station/
```

参数说明：

- `-n` 是演练，不会实际上传或删除文件。
- `--itemize-changes` 列出将发生的每项改动。
- `--delete` 会在正式同步时删除服务器中已被本地代码删除的旧文件。
- 被 `--exclude` 排除的 `.env` 和 `backups` 不会被覆盖或删除。

仔细检查输出中的：

```text
*deleting
```

只有确认待删除的都是已从代码库移除的旧文件，才能执行正式同步。

## 7. 正式同步代码

确认演练结果正确后，执行正式命令。与上一节唯一的关键区别是将 `-avzn` 改为 `-avz`：

```bash
rsync -avz --delete --itemize-changes \
  --exclude '.git' \
  --exclude '.env' \
  --exclude '.DS_Store' \
  --exclude '.venv' \
  --exclude '.pytest_cache' \
  --exclude '.ruff_cache' \
  --exclude 'frontend/node_modules' \
  --exclude 'frontend/dist' \
  --exclude 'frontend/*.tsbuildinfo' \
  --exclude 'frontend/vite.config.js' \
  --exclude 'frontend/vite.config.d.ts' \
  --exclude '*.db' \
  --exclude 'backups' \
  -e 'ssh -o IdentitiesOnly=yes -i /Users/markov/Desktop/mac_air.pem' \
  '/Users/markov/Desktop/token中转站/' \
  root@47.253.135.70:/opt/token-station/
```

同步完成后，不要立即删除本地 Git 历史，也不要重新生成服务器的 `.env`。

## 8. 在服务器重建服务

登录服务器：

```bash
ssh -o IdentitiesOnly=yes \
  -i /Users/markov/Desktop/mac_air.pem \
  root@47.253.135.70
```

执行：

```bash
cd /opt/token-station

chmod 755 scripts/*.sh deploy/nginx/entrypoint.sh

docker compose config --quiet

if grep -qx 'TLS_ENABLED=true' .env; then
  echo 'OK: TLS_ENABLED=true'
  docker compose up -d --build
  docker compose ps
else
  echo 'ERROR: TLS_ENABLED 不是 true，未执行重建'
fi
```

说明：

- `docker compose config --quiet` 无输出表示 Compose 配置格式正确。
- TLS 检查输出 `OK: TLS_ENABLED=true` 后才继续重建；如果不是 `true`，命令会主动停止发布。
- API 容器启动时会自动执行 `alembic upgrade head`。
- 带有新 Alembic 迁移时，发布前的数据库备份尤其重要。
- 不要再次运行 `./scripts/enable-tls.sh`；证书已签发并保存在 Docker 卷中。

## 9. 技术验收

### 9.1 检查容器

```bash
cd /opt/token-station
docker compose ps
```

期望：

- `api` 为 `healthy`。
- `postgres` 为 `healthy`。
- `redis` 为 `healthy`。
- `nginx` 为 `Up`，并映射 80/443。

### 9.2 检查健康接口

```bash
curl -fsS https://tokenshare.asia/health/live
echo

curl -fsS https://tokenshare.asia/health/ready
echo
```

Ready 预期类似：

```json
{
  "status": "ok",
  "checks": {
    "database": true,
    "redis": true,
    "migrations": true
  }
}
```

### 9.3 检查最近日志

```bash
docker compose logs --since=10m --tail=200 api nginx
```

重点排查：

- Python traceback。
- Alembic 迁移失败。
- API 容器反复重启。
- Nginx 502/504。
- 连续大量 5xx。

公网服务上线后很快出现自动扫描是正常现象；要关注的是系统是否正确返回安全响应，而不是扫描请求本身。

## 10. 业务验收

每次发布至少完成：

1. 浏览器打开 `https://tokenshare.asia`。
2. 管理员登录成功。
3. 用户额度和日志页正常。
4. 至少执行一次非流式模型调用。
5. 如果本次修改涉及 SSE，再执行一次流式调用。
6. 管理员调用日志中的状态、Token 和延迟正常。
7. 日志中没有真实上游 Key 或对话正文。

所有技术和业务验收通过后，才算发布完成。

## 11. 代码回滚

如果新版本出现问题，优先在 Git 中创建一个反向提交，不要强制改写已推送的历史。

在 Mac 执行：

```bash
cd '/Users/markov/Desktop/token中转站'
git log --oneline
git revert BAD_COMMIT_ID
git push origin main
```

将 `BAD_COMMIT_ID` 替换为 `git log --oneline` 中确认有问题的提交 ID。

然后重新执行本文第 5–9 节：

1. 再做一份线上数据库备份。
2. rsync 演练。
3. rsync 正式同步。
4. `docker compose up -d --build`。
5. 重新完成健康检查和业务验收。

如果问题仅来自应用代码，一般不需要恢复数据库。

## 12. 数据库恢复

只在数据库迁移或业务写入已经破坏数据时考虑恢复。

在服务器查看备份：

```bash
cd /opt/token-station
ls -lh backups
```

明确选择一个备份后执行：

```bash
CONFIRM_RESTORE=yes \
  ./scripts/restore.sh backups/token-station-20260818T010203Z.sql.gz
```

上面的时间戳只是格式示例；执行前必须用 `ls -lh backups` 中明确选定的实际文件名替换。

数据库恢复会用备份内容覆盖当前数据，备份之后新产生的用户、Key、配置、额度和调用账本都可能丢失。执行前应再备份一次当前状态。

## 13. 明确禁止的操作

不要执行：

```bash
docker compose down -v
```

`-v` 会删除 PostgreSQL、Redis 和 Let’s Encrypt 证书卷。

不要：

- 将本地 `.env` 上传到服务器。
- 将服务器 `.env` 提交到 GitHub。
- 在正常更新时重新生成 `TOKEN_ENCRYPTION_KEY`。
- 在没有备份时运行数据库迁移。
- 跳过 rsync 演练直接使用 `--delete`。
- 用 `git push --force` 覆盖生产版本历史。
- 将 PostgreSQL 5432、Redis 6379 或 API 8000 开放到公网。
