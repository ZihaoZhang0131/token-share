# 聊天与编码模式接入指南

本次版本增加无状态 Responses、客户端编码工具循环，以及固定推理档位。入口仍是 `https://tokenshare.asia`，使用原来的账号登录，不需要更换已有中转 Key。

## 1. 两种模式的区别

| 场景 | 接口 | 客户端参数 | 工具执行位置 |
| --- | --- | --- | --- |
| 普通对话、图片输入、结构化输出 | `POST /v1/chat/completions` | `messages`、`reasoning_effort`、`max_completion_tokens` | 支持哪些工具取决于上游；Sol 工具调用改用编码接口 |
| 编码助手、多轮工具调用、流式 Agent | `POST /v1/responses` | `input`、`reasoning.effort`、`max_output_tokens` | 客户端本机；中转服务器不执行命令 |

两者都支持 JSON 与 SSE，共享账号月额度、Key 的 RPM/TPM 与模型授权。这里的“编码模式”是供 SDK / Codex 等客户端接入的 API，并非网站内置 IDE 或在线终端。控制台提供配置、用量和可复制示例。

## 2. 管理员如何配置

1. 上游的 Base URL 使用 `https://api.openai.com/v1`，配置有对应模型权限的 OpenAI API Key。Key 只保存在服务端加密数据库；不要将它填写进用户客户端。
2. 在“模型 → 新增模型”填写公开别名、上游真实模型名、上游服务。
3. 接入模式选择“聊天”“编码”或“聊天 + 编码”。只有上游支持两种接口时才选双模式。
4. 固定推理强度：留空意味着由客户端/上游默认决定；选择档位后，服务器强制绑定，不允许客户端用同一别名覆盖成其他档位。
5. “最大输出 Token”包含推理 Token 和可见回答，**不是最大输入或上下文窗口**。建议从 16,384 开始，用户/Key 的 TPM 必须足够覆盖估算输入 + 本次输出上限。客户端应主动传较小上限，避免每次默认预留全额。
6. 在用户编辑页勾选新增别名；创建路由本身不会让所有用户自动获得权限。

GPT-6.1 Sol 的五个别名示例：

| 用户使用的公开模型名 | 上游模型名 | 固定推理强度 | 接入模式 |
| --- | --- | --- | --- |
| `gpt-6.1-sol-low` | `gpt-6.1-sol` | `low` | 双模式 |
| `gpt-6.1-sol-medium` | `gpt-6.1-sol` | `medium` | 双模式 |
| `gpt-6.1-sol-high` | `gpt-6.1-sol` | `high` | 双模式 |
| `gpt-6.1-sol-xhigh` | `gpt-6.1-sol` | `xhigh` | 双模式 |
| `gpt-6.1-sol-max` | `gpt-6.1-sol` | `max` | 仅 Responses |

2026-11-01 扩展目录及真实调用核验见 [OpenAI 模型目录](OpenAI模型目录与档位-2026-11-01.md)。GPT‑6 / GPT‑5.6 系列的 `max` 经线上实测仅被 Responses 接受，Chat 请求会在中转站返回 422 并提示使用 Responses；不自动降档。

它们不是五个独立上游模型，而是同一模型的五条参数路由。例如 `high` 别名会在 Chat 请求注入 `reasoning_effort="high"`，在 Responses 注入 `reasoning={"effort":"high"}`。客户端传不同值会在调用上游前得到 422，不消耗模型 Token。Sol 不接受 `none` / `minimal`；控制台为其他模型保留这两个选项，但对 Sol 会拒绝保存。

## 3. 用户接入聊天

安装最新版官方 Python SDK：`pip install -U openai`。通过安全的环境变量管理方式设置 `TOKEN_STATION_KEY` 为自己的中转 Key，不是管理员上游 Key。不要把 Key 提交到 Git。

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["TOKEN_STATION_KEY"],
    base_url="https://tokenshare.asia/v1",
    max_retries=0,
)
reply = client.chat.completions.create(
    model="gpt-6.1-sol-low",
    messages=[{"role": "user", "content": "用一句话解释递归。"}],
    max_completion_tokens=2048,
)
print(reply.choices[0].message.content)
```

Sol 推理模式不要传 `temperature`、`top_p`、`logprobs`、`top_logprobs`。兼容旧客户端的 `max_tokens` 会为 Sol 转为 `max_completion_tokens`，但不要同时提交两种上限。

## 4. 编码工具循环

继续使用上述 `client`：

```python
tools = [{
    "type": "function",
    "name": "read_project_file",
    "description": "读取固定示例文件",
    "parameters": {
        "type": "object", "properties": {},
        "required": [], "additionalProperties": False,
    },
    "strict": True,
}]
history = [{"role": "user", "content": "读取项目文件并解释功能。"}]
for _ in range(4):
    reply = client.responses.create(
        model="gpt-6.1-sol-low", input=history, tools=tools,
        store=False, max_output_tokens=2048,
    )
    # 必须保留 reasoning / encrypted_content 等全部输出项。
    history.extend(reply.output)
    calls = [item for item in reply.output if item.type == "function_call"]
    if not calls:
        print(reply.output_text)
        break
    for call in calls:
        # 工具由客户端执行；真实应用需路径限制、权限校验与危险操作确认。
        result = "def add(a, b): return a + b" if call.name == "read_project_file" else "未知工具"
        history.append({
            "type": "function_call_output", "call_id": call.call_id, "output": result,
        })
else:
    raise RuntimeError("达到工具循环上限，请人工检查")
```

无状态模式下，每一轮都传回完整历史。不要只回传回答文本而丢弃工具 call_id 或加密推理项；也不要使用 `previous_response_id`。

流式示例：

```python
with client.responses.stream(
    model="gpt-6.1-sol-low", input="写一个 Python 二分查找函数。",
    store=False, max_output_tokens=2048,
) as stream:
    for event in stream:
        if event.type == "response.output_text.delta":
            print(event.delta, end="", flush=True)
```

## 5. Codex CLI 配置

将下列片段**合并**到客户端 `~/.codex/config.toml`，先备份原文件，不要直接覆盖其他配置。当前 shell 需可读取 `TOKEN_STATION_KEY`。

```toml
model_provider = "token_station"
model = "gpt-6.1-sol-high"
model_reasoning_effort = "high"
web_search = "disabled"

[model_providers.token_station]
name = "Token Station"
base_url = "https://tokenshare.asia/v1"
env_key = "TOKEN_STATION_KEY"
wire_api = "responses"
requires_openai_auth = false
supports_websockets = false
request_max_retries = 0
stream_max_retries = 0
```

固定别名的客户端推理设置必须一致。使用已有不固定档位的 `gpt-6.1-sol` 别名时，可由客户端选择推理强度。客户端版本差异可能带来额外接口或工具；先用小型只读任务验收，再执行需要写文件或运行命令的任务。中转站没有执行命令的权限，但本机 Codex 仍需自己的沙箱和审批规则。

## 6. 兼容与安全边界

- Responses 仅支持同步 HTTP / SSE、客户端 `function` / `custom` 工具及其 `namespace`，不支持托管 web search、file search、code interpreter、远程 MCP、后台任务、WebSocket、`/responses/compact`。
- 强制 `store=false`；拒绝 conversation、previous_response_id、保存的 prompt、item_reference、上游 file_id / vector_store_ids / container_id，避免多个用户通过共享上游凭证读取其他人的资源。
- 不提供响应查询、删除、文件上传等共享上游资源接口。长会话需要客户端自行压缩历史或开始新会话。
- 不自动重试生成请求；连接失败返回 502，超时返回 504；SSE 已发响应头后使用安全错误事件，账本记录真实失败状态。客户端断开关闭上游连接。
- 正常返回 usage 时按实际输入/输出（包含推理）结算。缺少 usage 或中途断开时保守扣除本次预留量；仅凭可见文本无法可靠估计隐藏推理费用。
- 中转站不保存对话正文，日志只保存调用元数据；上游自身的数据政策仍适用。`store=false` 不等于承诺上游零保留。
- 额度估算默认 cl100k_base，并非保证与 Sol tokenizer 完全一致；真实 usage 优先。图片、工具模式与隐藏推理都会影响实际 Token。

## 7. 版本升级与回滚

数据库迁移 `0002` 只为 model_routes 增加 api_mode 和 reasoning_effort。旧路由默认保持 chat，不自动把其他上游改成双模式；旧 Key 和用户表不变。

先备份 PostgreSQL、源代码和旧镜像，再构建 api/nginx 并替换这两个容器；保留 PostgreSQL、Redis 和证书卷。按日常发布指南验证 `/health/ready` 的数据库、Redis、迁移三项均为 true。

如果回滚到只认识 `0001` 的旧程序，先暂停入口并保存当前数据库备份，再用**新镜像**运行 `alembic downgrade 0001`，然后恢复旧代码及镜像。降级会丢失本次新增的模式/固定档位配置；旧应用不支持新别名的固定推理，必须禁用这些别名或恢复发布前备份。不要在有新业务数据时直接覆盖整个数据库，也不要执行 `docker compose down -v`。
