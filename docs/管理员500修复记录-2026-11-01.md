# 管理员页面 500 修复记录

## 原因

此前双模式验收脚本通过 ORM 写入了 `@internal.invalid` 临时账号。这个保留域名不满足 EmailStr 校验；虽然账号及其 Key 已禁用，管理员用户列表仍读取该记录，在响应序列化时返回 500。其他五个管理接口正常，但前端 Promise.all 的整体失败导致正常结果也未展示。

之前的模型调用、Codex、访客页面验收不能代替登录后的管理台验收。本次问题说明发布后的账号数据校验与管理员全页签检查存在遗漏。

## 修复

1. 仅将出错的临时账号邮箱改为同名 `@tokenshare.asia` 地址，保持停用、所有 Key 撤销、密码不变；写入修复审计，不删除历史账本。
2. User ORM 的邮箱写入增加与 API 输入一致的校验，维护脚本也不能直接赋值保留域名邮箱。
3. UserView 输出已有邮箱字符串，不重新套用创建时的 EmailStr 校验，避免一条历史记录破坏整个列表。登录和创建用户的输入仍严格校验。
4. 管理台六类数据独立加载，成功部分即时显示，失败部分保留上次数据，并明确标注失败接口、可能存在旧数据及刷新方式。刷新期间禁用重复点击，过时请求不覆盖新数据。

## 回归测试

- 后端：40 项通过。新增 ORM 拒绝非法邮箱、合法邮箱规范化、活跃/停用历史异常账号的六管理接口读取，以及 API 继续拒绝非法新账号测试。
- 前端：`cd frontend && npm test`，2 项通过。验证单接口 500 不阻塞其余五项、失败不覆盖旧数据、快请求不等待慢请求、重试恢复。
- TypeScript/Vite 构建、Ruff、diff 检查通过。
- 在线数据修正后，通过用户浏览器原有管理员会话确认调用日志和用户列表恢复，未重置任何账号密码或读取上游 Key。

## 发布验收要求

部署后必须在已登录管理员会话中刷新，并检查总览、上游、模型、用户、调用日志和审计日志；同时在服务端确认六接口返回 200。健康检查只验证服务依赖，不代表管理台业务请求通过。

今后的验收账号通过正常创建接口或同等校验创建，完成清理后再次读取管理员用户列表，不将“Key 已撤销”视为测试数据完全无副作用。
